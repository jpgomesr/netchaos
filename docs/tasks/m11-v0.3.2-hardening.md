## M11-1 — `#127`: test package compiles on 32-bit

**Status:** done — #128
**Issue:** #127 (NC-09 of #117)
**Depends on:** —
**Blocks:** `M11-3`

**Cause:** three `serializationDelay` overflow tests in `bandwidth_test.go` (added for #80 in `v0.3.0`) pass untyped constants above 2³¹ where an `int` is expected, so the test package does not compile when `int` is 32 bits. The library itself always built.

**Scope:**
- `bandwidth_test.go`: a helper `intOrSkip(t, v int64) int` takes the sizes and rates as `int64` and skips when the value exceeds `math.MaxInt`. On 32-bit no `Write` can be that large (`len` is an `int`), so the overflow path these tests guard cannot occur there. On 64-bit nothing changes: the three tests still run.
- `.github/workflows/ci.yml`: a `32-bit (GOARCH=386)` step on the `stable` leg running `go vet ./...` and `go test ./...`; 386 binaries run natively on the amd64 runners.

**Red:** `GOARCH=386 go vet ./...` failed with 9 `(overflows)` errors in `bandwidth_test.go`.

**Done when:** `GOARCH=386 go vet ./... && GOARCH=386 go test ./...` is green locally and in CI.

## M11-8 — `#118` NC-30: more fuzzing

**Status:** done — #136

**Finding while fuzzing:** within a second, `FuzzEvaluatorAccounting` reached `bufBytes = 71` against a bound of 64 with several buffered payloads, which the raw-pipe invariant (`checkPipeAccounting`: past the bound only via one oversized write) forbids. It is documented behaviour, not a bug: `WithDuplication` charges the second copy against the bound after admission ([docs/05 § Packet duplication](../05-fault-injection.md#packet-duplication), "Accounting"). The evaluator target therefore checks `bufBytes` == buffered payloads (shared with the raw-pipe check) and `bufBytes <= bound + maxWrite`; the input stays in `testdata/fuzz/FuzzEvaluatorAccounting/` as a regression case.

`FuzzSplitAddr`, `FuzzEvaluatorAccounting` (inside synctest, faults toggled mid-stream), `FuzzStreamIntegrity` and `FuzzSerializationDelay` (against `math/big`), each with a committed corpus and a 10–20 s CI step next to `FuzzPipeAccounting`.

## M11-9 — `#118` NC-31: `Network`-path benchmarks

**Status:** done — #137

**Baseline** (`go test -run='^$' -bench=. -benchmem -count=5`, median of 5; go1.25.0 linux/amd64, Intel Xeon @ 2.10GHz, 4 vCPU, shared cloud runner — compare runs on the same machine, not across machines):

| Benchmark | ns/op | B/op | allocs/op |
|---|---:|---:|---:|
| `BenchmarkDialAccept` | 18,543 | 5,774 | 45 |
| `BenchmarkNetworkRoundTrip/nofault` | 1,096 | 1,152 | 4 |
| `BenchmarkNetworkRoundTrip/latency` | 3,554 | 1,278 | 7 |
| `BenchmarkNetworkRoundTrip/loss` | 1,453 | 1,152 | 4 |
| `BenchmarkNetworkRoundTrip/bandwidth` | 3,739 | 1,308 | 7 |
| `BenchmarkNetworkRoundTrip/all` | 3,845 | 1,283 | 7 |
| `BenchmarkTrace` (100,000 events) | 21,817,971 | 49,514,720 | 31 |
| `BenchmarkManyConns` (1,000 conns) | 1,191 | 973 | 4 |
| `BenchmarkRoundTrip` (raw pipe, M6-7) | 530 | 760 | 4 |
| `BenchmarkWriteUnderLoss` (raw pipe, M6-7) | 1,266 | 1,016 | 2 |
| `BenchmarkWriteUnderLatency` (raw pipe, M6-7/M6-8) | 1,349 | 904 | 1 |

Reading it:
- A fault-free round trip through a `Network` costs about twice the raw pipe (≈1.1 µs vs ≈0.5 µs): the evaluator, the live-config lock and one trace event per write.
- Latency and bandwidth add ≈2.5 µs each, almost all of it the real `time.AfterFunc` firing and waking the reader — outside a synctest bubble even a 1 ns delay goes through the timer. Turning on every stage costs no more than one timing stage.
- 1,000 open connections do not slow a round trip measurably (1.19 µs vs 1.10 µs).
- `Trace()` over 100,000 events takes ≈22 ms and allocates ≈49.5 MB (≈495 B/event): the output slice grows by `append` without a size hint. Not changed here (out of scope); it is input for #115's NC-08 (trace growth and cost).
- `DialAccept` varies more run to run (13–44 µs) than anything else: it is dominated by goroutine hand-off scheduling.

CI runs every benchmark once (`-benchtime=1x`) so a broken benchmark is caught; timings are not checked.

`BenchmarkDialAccept`, `BenchmarkNetworkRoundTrip/{nofault,latency,loss,bandwidth,all}`, `BenchmarkTrace` (100,000 events) and `BenchmarkManyConns`, with a baseline table recorded here as `M6-7` did.
