## Sequencing

Unlike M6, this milestone **is** a build, so the order matters. Three edges are load-bearing; the rest is preference.

```
M7-1  ────────────────────────────────▶  everything else
      (addresses gain host:port — rewrites every address string,
       so anything landing after it rebases cleanly)

M7-3  ──▶ M7-4          (contract before setters — see M7-3)
M7-5  ──▶ M7-6          (the throttle is what makes the pipe bound observable)
M7-5..M7-9  ──▶ M7-10   (the exported event shape must cover every fault kind)
```

**`M7-4` before `M7-5` is a preference, not a dependency**, and is worth stating because it looks like one. `faultPolicy` is a copied struct captured in `installFaultPolicy`'s closure (`faults.go`), so a throttle stage is additive either way. The reason to put the setters first is that they convert loss and latency from copied values to synchronized live reads; adding the throttle afterwards means writing it once against the final read mechanism instead of adding a fourth copied field and converting it a task later.

### M7-1 — Addresses gain a synthesized host:port shape

**Status:** done
**Issue:** [#49](https://github.com/jpgomesr/netchaos/issues/49) — decided by `M6-10`
**Depends on:** —
**Blocks:** every other task in this milestone, by rebase cost rather than by logic

**Objective**
`peerName` is the identity function (`addr.go:32`): the string passed to `Listen`/`Dial` **is** the peer name, and `addr.String()` returns it verbatim. So `net.SplitHostPort(c.RemoteAddr().String())` fails against netchaos where it succeeds against the real stack, and any code under test that wants the host half — logging, metrics labelling, allow-listing — pays a cost it does not pay against `net`. That is the specific friction [01 — Vision](../01-vision.md) says netchaos exists to remove. `Listen` also has no `:0` ephemeral-port equivalent.

**Must land before `v1.0.0`**, per `M6-10`: adding port structure afterwards is a breaking change to every address string a test prints.

**Scope**
- `addr` gains a `port` field; `String()` returns `net.JoinHostPort(host, port)`.
- `peerName` stops being the identity function and becomes a real parse returning the **host half**, stripping an optional `:port`. `addr.go`'s type comment currently guarantees *exactly one place* the address-to-peer relationship is defined; that property has to be **re-established deliberately**, not assumed — rewrite the comment rather than leaving it stale.
- `Listen("tcp", "server")` keeps working and yields `server:<port>`. `Listen("tcp", "server:8080")` honours the explicit port. `Listen("tcp", "server:0")` assigns a synthesized one, closing the missing ephemeral-port case.
- Port assignment: a sequential counter on `Network` from a base, mirroring `nextOrdinal`, advanced in `Listen`/`Dial` order. That order is **already fixed by the determinism contract**, so this widens nothing. State the matching caveat: the contract's own limit is that concurrent, unordered establishment is not covered, so two goroutines racing to `Listen` get nondeterministic ports — and unlike an ordinal, a port is visible in `RemoteAddr().String()` and therefore in test failure output. Existing nondeterminism, newly visible.
- Out of scope: any change to how ordinals or RNG streams are derived. Addresses are not an input to `deriveStream` and must not become one.

**Two sub-decisions this task must answer explicitly**

1. **What `Partition("server")` means once the peer is `server:<port>`.** `M6-10` named this as the open question inside the decision. Recommended: identity stays the **host half only**, so `Partition("server")` and `Partition("server:8080")` name the same peer and every existing call keeps working. `newPairKey` continues to take names, not addresses.
2. **Unnamed dialers.** An unnamed dialer's identity today is the whole string `ephemeral:N` — which, after this change, parses as host `ephemeral` plus port `N`, collapsing every unnamed dialer onto one host and making them indistinguishable to `newPairKey`. Recommended: host `ephemeral-N`, port `N`. Whatever is chosen, uniqueness has to be preserved on purpose rather than by accident.

**Files**
- `addr.go` — `addr`, `peerName`, the type comment
- `netchaos.go` — `Listen`, `DialContext`'s synthesized name, the port counter
- `partition.go` — `peerName` callers
- `example_test.go` and every test asserting an address string
- `docs/04-api-design.md` — the dialing/listening section
- `CHANGELOG.md`

**Acceptance criteria**
- [x] `net.SplitHostPort(c.RemoteAddr().String())` succeeds and returns the listen name as the host. — `TestSplitHostPortOnRemoteAddr`, red with `address server: missing port in address`.
- [x] `Listen("tcp", "server")`, `"server:8080"` and `"server:0"` all behave as described above.
- [x] `Partition`/`Heal` still target a peer named without a port, and the sub-decision is recorded in `addr.go`'s type comment.
- [x] Two unnamed dialers have distinct identities. — red beforehand: both were host `ephemeral`.
- [x] `addr.go`'s type comment states the new address-to-peer rule, and there is still exactly one function deriving one from the other.
- [x] `testdata/traces/*.golden` are **byte-identical** — they carry no addresses (`ord side seq part drop drawn_ns eff_ns`), so a diff here would mean something unintended happened (`M3-3`).
- [x] `-race` clean on CI. — confirmed on PR #57: `test (1.25)` and `test (1.26)` (both run `go test -race ./...`) pass, along with `lint` and the `gofmt` check. Ticked from the CI run rather than a local one, as `M6-1` was: `-race` needs `CGO_ENABLED=1`, and this dev machine has no C toolchain (`AGENTS.md`).

**Tests**
- Red first: `TestSplitHostPortOnRemoteAddr` fails today because the address is bare.
- `TestSplitHostPortOnRemoteAddr`, `TestListenHonoursExplicitPort`, `TestListenEphemeralPortIsAssigned`, `TestPartitionTargetsHostHalf`, `TestUnnamedDialersHaveDistinctIdentities`, `TestPeerNameStripsAnExplicitPort`
- Verify: `go build ./... && go vet ./... && gofmt -l . && go test -race ./... && golangci-lint run`

**How it was resolved**

Both sub-decisions were answered as recommended, and a third surfaced during implementation.

1. **Identity is the host half.** `peerName` now delegates to a new `splitAddr` and returns the host, so `"server"` and `"server:8080"` name the same peer and `newPairKey` still takes names rather than addresses. `addr`'s type comment was rewritten around the host-is-identity / port-is-presentation split, which is what re-establishes the "exactly one place" property `M6-10` required be deliberate: `splitAddr` is the single parse and `peerName` is the identity projection over it.
2. **Unnamed dialers are `ephemeral-N`, not `ephemeral:N`.** The dash is load-bearing. `TestUnnamedDialersHaveDistinctIdentities` was red *before any production change* — the old name already parsed as host `ephemeral` plus port `N`, so the moment addresses gained structure every unnamed dialer in a `Network` would have collapsed onto one identity and a `Partition` naming it would have hit all of them.
3. **`WithPeerName` strips a port too.** Not in the task text, found while implementing: a peer name is an identity, but callers reach for the same strings they pass to `Dial`. Without stripping, `WithPeerName(ctx, "client:1234")` would target a peer `Partition("client")` could never name.

**Port assignment.** Two sources rather than one counter, because it makes failure output read like the real thing: listeners take a counter from `listenPortBase = 8000` in `Listen` order, and a dialing side takes `ephemeralPortBase + ordinal` (32768+, wrapping). Deriving the dialer's port from its ordinal rather than a counter of its own means it inherits the determinism contract's accounting for free — a dial that never establishes never takes an ordinal, so it never shifts any other connection's port either.

**A malformed address is a `*net.AddrError`**, not a new sentinel. The standard library already has the right error for this, and `M6-2`'s uniform `*net.OpError` wrapper carries it, so nothing was added to the exported surface.

### M7-2 — Network.DialerFor: make a drop-in dialer partition-targetable

**Status:** done
**Issue:** [#36](https://github.com/jpgomesr/netchaos/issues/36) — **decided in this milestone**, see the banner
**Decision:** **`Network.DialerFor(name string) func(network, addr string) (net.Conn, error)`.** Chosen over `DialAs(name, network, addr)` and a `WithDefaultPeerName` option because it is the only one of the three that keeps the `net.Dial` shape the adoption claim rests on: the caller still hands their client one `func(network, addr string) (net.Conn, error)`. `DialAs` moves the friction rather than removing it — `myservice.NewClient(n.DialAs)` does not compile — and a Network-wide default name allows only one named dialer per `Network`, which breaks multi-client scenarios.
**Depends on:** `M7-1` (rebase cost only)
**Blocks:** —

**Objective**
`WithPeerName` records a dialer's identity on a `context.Context`, and `Dial(network, addr string)` has no context parameter. So a `Dial` call can never carry a peer name, is never partition-targetable, and never blocks on a partition. Partition is a headline feature and `Dial` is the entry point the no-rewrite adoption claim rests on; a user who wants both currently has to abandon the drop-in and switch to `DialContext`.

**Scope**
- Add `DialerFor`, closing over `n.DialContext(WithPeerName(context.Background(), name), network, addr)`. The implementation is thin **by design**: it reuses the existing named-dialer path in `DialContext` and adds no new partition logic.
- Document the behaviour it inherits: a `DialerFor` dialer **is** subject to the dial-time partition check, so it blocks against a partitioned peer until `Heal`, with no context to bound it. That is correct — a partition drops the SYN — but it is new for anyone who reached for `Dial` precisely because it never blocked. Point at `DialContext` for the bounded form.
- Out of scope: changing `Partition`'s silent no-op on unknown names. `M5-2` finding F3 decided it stays, and this task removes the *cause* of the composed failure rather than the no-op itself.

**The doc sweep is the larger half of this task.** "A named dialer requires `DialContext`" is asserted in four places, and `DialerFor` falsifies all four:

- `docs/04-api-design.md` — *"`Dial` is always in that second category."*
- `addr.go` — `peerNameCtxKey`'s comment on `Dial`'s signature having no room for an identity
- `addr.go` — `WithPeerName`'s godoc
- `partition.go` — `Partition`/`Heal`'s godoc, the cross-reference `M6-9` landed **specifically because the limitation was believed permanent** (its own text: *"the caveat is now known to be permanent for `Dial`"*)

`M6-9`'s rationale is superseded here. Its godoc cross-reference stays — an unnamed `n.Dial` is still not targetable — but the "permanent" framing must go, or two `done` docs contradict each other.

**Files**
- `netchaos.go` or `addr.go` (next to `WithPeerName`), `partition.go`, `docs/04-api-design.md`, `example_test.go`, `dial_test.go`, `partition_test.go`, `README.md` if it shows the partition example, `CHANGELOG.md`

**Acceptance criteria**
- [x] A connection dialed through `DialerFor("client")` is affected by `Partition("client", "server")`. — `TestDialerForIsPartitionTargetable`.
- [x] The returned value is assignable to `func(network, addr string) (net.Conn, error)`, asserted at compile time — by the explicit variable declaration in the test and in `ExampleNetwork_DialerFor`.
- [x] The blocking-on-partition behaviour is documented on `DialerFor` and asserted by a test. — `TestDialerForBlocksOnStartPartitioned`.
- [x] **No godoc or doc page still says a partition-targetable dialer requires `DialContext`.** — six sites swept, listed below.
- [x] `docs/04`'s frozen-surface list includes `DialerFor`.
- [x] `-race` clean on CI. — confirmed on PR #58: `test (1.25)`, `test (1.26)`, `lint` and the `gofmt` check all pass. The first `lint` run failed on staticcheck `ST1023` over the dial-shape assertion; it is now expressed as a function parameter, which keeps the compile-time check and satisfies the linter.

**How it was resolved**

The implementation is four lines, which is the argument for the option: `DialerFor` closes over `WithPeerName(context.Background(), name)` and calls the existing `DialContext`, so it reuses the whole named-dialer path and adds no partition logic of its own.

The doc sweep was the larger half, as the task predicted, and it was six sites rather than the four listed:

1. `docs/04` — the "`Dial` is always in that second category" paragraph, now stating that the limitation belongs to `Dial` rather than to `net.Dial`-shaped dialing, with all three forms side by side.
2. `docs/04` — the `WithPeerName` addition note, which described the gap `DialerFor` now closes.
3. `docs/04` — the dial-time partition effect ("named itself via `WithPeerName`" → "via `WithPeerName` or `DialerFor`").
4. `docs/05` — the same claim in the partition section.
5. `addr.go` — `peerNameCtxKey`'s comment and `WithPeerName`'s godoc.
6. `partition.go` — `Partition` and `Heal`'s godoc, which now show both ways to name a dialer.

**`M6-9`'s "permanent" framing is superseded, and its task text now says so.** M6-9 recorded the caveat as permanent for anything with `Dial`'s shape; that over-generalized a limitation belonging to `Dial` specifically. Its godoc cross-reference stays — an unnamed `n.Dial` is still not targetable — but it now points at two ways to name a dialer instead of describing a dead end.

Also swept: three stale `ephemeral:N` spellings left by `M7-1`, in `docs/04`.

**Tests**
- Red first: `TestDialerForIsPartitionTargetable` — a compile error, since no such method exists.
- `TestDialerForIsPartitionTargetable`, `TestDialerForBlocksOnStartPartitioned`

### M7-3 — Widen the determinism contract for runtime fault mutation

**Status:** done
**Issue:** [#50](https://github.com/jpgomesr/netchaos/issues/50) — decided by `M6-13`
**Decision (both questions, by the maintainer):** the setters **join the contract's ordered list** of calls, and a mid-run change **applies to already-established connections**, matching `Partition`/`Heal`.
**Depends on:** —
**Blocks:** `M7-4`

**Objective**
Documentation only, and **the sequencing is the substantive part of the decision, not a formality.** #50 is emphatic: *"Rewrite the contract before implementing the setters, not after. The contract is the library's core promise and its current wording is deliberately narrow; widening it is the real decision inside this change, and doing it retroactively would mean the implementation had already picked an answer."* `docs/04` carries that instruction at the contract itself.

**Scope**
The contract today fixes only *"the order in which `Dial`, `Listen`, `Partition`, and `Heal` are called."* Rewrite it to cover a mid-run configuration change, answering three things:

- Whether `SetLatency`/`SetPacketLoss` join that ordered list. Recommended: yes — they are the same class of call as `Partition`/`Heal`.
- Whether a mid-run change applies to **already-established connections** (as `Partition` does) or only to subsequent dials. This is #50's own named open question. Recommended: already-established, matching `Partition`, since "healthy, then degraded, then healthy" on a live connection is the entire motivation.
- What it does **not** guarantee: a setter racing in-flight I/O on another goroutine has no defined per-unit boundary — the same shape of limit the contract already states for concurrent `Dial`.
- Out of scope: writing any of `M7-4`'s code, including the field layout.

**Files**
- `docs/04-api-design.md` — the determinism contract
- `docs/05-fault-injection.md` — if it restates the construction-time framing
- `options.go` — `WithSeed`'s godoc carries a condensed copy of the contract

**Acceptance criteria**
- [x] The contract names the setters, answers the established-connections question, and states the new limit. — new **Runtime fault mutation** subsection in `docs/04`.
- [x] `WithSeed`'s godoc and `docs/04` say the same thing as each other.
- [x] No behaviour change; golden vectors and traces untouched.

**Tests**
- None — prose only. Verify with `go build ./... && go vet ./... && gofmt -l . && go test -race ./...` still passing unchanged.

**How it was resolved**

Both questions answered yes, by the maintainer, before any of `M7-4` was written — which was the point of separating this task.

1. **The setters are ordered calls**, joining `Dial`, `Listen`, `Partition` and `Heal` in the guarantee. A setter racing other `Network` calls is nondeterministic for the same reason a racing `Dial` is, and has the same fix.
2. **A change applies to already-established connections.** That is the motivation — "healthy, then degraded, then healthy" on a live connection without rebuilding the `Network` and resetting every ordinal — and it makes the setters symmetric with `Partition`/`Heal` rather than a differently-shaped thing sharing a noun. The consequence `M7-4` inherits: a connection's fault configuration is read **per unit** rather than captured at dial time.

**Two things the rewrite says that were not in the question**, both because they are easy to assume wrong:

- **Draw discipline does not change.** Every configured fault still draws unconditionally on every unit past the partition gate. `SetLatency(0, 0)` changes the *value* a draw produces, not whether the draw happens — so disabling a fault mid-run saves no draws, and re-enabling one does not resume a paused stream. Enabling a kind that was never configured does begin drawing from that kind's stream, which shifts nothing else, since kinds are independent by derivation.
- **The new limit.** The contract fixes a setter's order against other `Network` calls, *not* against in-flight I/O on another goroutine: if one goroutine writes in a loop while another calls `SetPacketLoss`, which unit first sees the new rate is the scheduler's choice, not the seed's. There is no per-unit boundary the contract can honestly name, so it prescribes sequencing instead — write, then set, then write.

`docs/04`'s accepted-additions list no longer describes the setters as gated; the gate is this task.

### M7-4 — SetLatency and SetPacketLoss

**Status:** done
**Issue:** [#50](https://github.com/jpgomesr/netchaos/issues/50) — decided by `M6-13`
**Depends on:** `M7-3` — **not reorderable**, see that task
**Blocks:** —

**Objective**
`Partition`/`Heal` change behaviour on live connections; latency and loss are fixed at construction. A test wanting "healthy, then degraded, then healthy" has to build a second `Network`, which means new connections and a reset of every ordinal. It is an asymmetry in the mental model as much as a missing feature: someone who learns partition can be toggled mid-test reasonably expects the same of the other two.

**Scope**
- Add `SetLatency(min, max time.Duration)` and `SetPacketLoss(rate float64)` with `Partition`/`Heal`'s live semantics, as `M7-3` defined them.
- **The per-unit read path stops being lock-free**, accepted explicitly by #50 and not optional. `faultPolicy` stops carrying copied latency/loss values and reads them through `fp.network` under a mutex — the pattern already used for partition state via `fp.network.isPartitioned`, so this follows an existing mechanism rather than introducing one.
- Reuse `validateLatencyRange` (`latency.go`) and `validateLossRate` (`loss.go`) so a setter panics on an invalid value exactly as `NewNetwork` does, and say so in the godoc.
- Keep the `faultPolicy{network: nil}` case working — `faults.go` documents it as "no partition tracking," used by pipe-level tests that build a pipe without a `Network`.
- Out of scope: per-pair or per-direction scoping (`M6-16`, still gated), and a setter for any fault kind this milestone adds later.

**Files**
- `netchaos.go`, `faults.go`, `latency.go`, `loss.go`, `docs/04-api-design.md` (frozen-surface list), `CHANGELOG.md`
- `faults_test.go`, `latency_synctest_test.go`, `loss_test.go`

**Acceptance criteria**
- [x] A `SetLatency` call changes delivery timing on a connection established before it. — `TestSetLatencyAppliesToLiveConn` asserts exactly 50 ms in virtual time, then back to 0.
- [x] Same for `SetPacketLoss`. — `TestSetPacketLossAppliesToLiveConn` reads `"aabb"`: the middle write is dropped by a rate set after the connection existed.
- [x] Invalid values panic with the same message shape as the equivalent option.
- [x] A setter racing concurrent I/O is `-race` clean on CI. — confirmed on PR #62: `test (1.25)` and `test (1.26)` (both run `go test -race ./...`) pass, along with `lint`, `CodeQL` and the two `Analyze` jobs.
- [x] `testdata/traces/*.golden` unaffected — no scenario in them calls a setter. Verified byte-identical.

**Tests**
- Red first: `TestSetLatencyAppliesToLiveConn` — a compile error, then a timing assertion in virtual time under `synctest`.
- `TestSetLatencyAppliesToLiveConn`, `TestSetPacketLossAppliesToLiveConn`, `TestSettersPanicOnInvalidValues`, `TestSettersRaceWithLiveIO` (new `setters_test.go`)
- Verify: `go build ./... && go vet ./... && gofmt -l . && go test -race ./... && golangci-lint run`

**How it was resolved**

The shape that made this small: `faultPolicy` stopped *holding* the configuration. It held copies taken at dial time, which is precisely what made a connection's faults unchangeable for its lifetime. It now holds a `*Network` and reads a `faultConfig` from it per unit — so the live semantics fall out of removing the copy rather than out of new machinery.

Three details worth recording:

- **The configuration is read as one value, not field by field.** `faultConfig` is copied out under a single `RLock`, so a unit is evaluated against one configuration and never a mix of the one before a setter call and the one after it.
- **The `network == nil` case survives** as `faultPolicy.static`. That case belongs to pipe-level tests that build a pipe without a `Network`; keeping the fallback meant the six existing `installFaultPolicy` call sites needed only a `static:` wrapper rather than a rewrite.
- **Validation is the existing `validateLatencyRange`/`validateLossRate`**, so a setter panics with the message naming `WithLatency`/`WithPacketLoss` — the same text the option produces, since it is the same programmer error.

**One bug, in the test rather than the code.** `TestSettersRaceWithLiveIO` deadlocked on the first run: the reader goroutine was in the same `WaitGroup` as the writer and the setter, but it only exits when `done` closes, and `done` closed after `wg.Wait()`. The reader now has its own group and is drained after the two goroutines under test finish. Worth noting because the symptom was a hung suite, not a failing assertion.

### M7-5 — Fault kind: bandwidth throttling

**Status:** done
**Issue:** [#53](https://github.com/jpgomesr/netchaos/issues/53), candidate 1 — decided by `M6-11`
**Decision (both open sub-decisions, by the maintainer, before implementation):** the throttle is **deterministic and draws nothing** — no `kindThrottle` byte, no stream — and composes **additively** with `WithLatency`. See "How it was resolved" for why, and for the amendment this makes to the task text below.
**Depends on:** `M7-4` (preference, not a dependency — see Sequencing)
**Blocks:** `M7-6`, `M7-10`

**Objective**
`docs/06` calls this "worth doing first of the four": it is purely a delivery-timing model, and it composes as a fourth stage in `faults.go`'s evaluator alongside latency. "The link is slow" is a first-class thing tests want.

**Scope**
- ~~A new `faultKind` (`kindThrottle`) in `rand.go`~~ **Superseded — see "How it was resolved."** `rand.go` is untouched: the throttle delay is `size ÷ rate`, a deterministic function with nothing to draw. A fourth stage in `installFaultPolicy` (`faults.go`), still in scope.
- ~~**The draw discipline is not negotiable** (`M2-5`, restated by #53): the new kind draws **unconditionally** on every unit past the partition gate, like the existing two.~~ **Does not apply to this kind.** The discipline binds fault kinds that draw from a stream; a kind with no stream has no draw index to misalign, so it cannot violate a discipline about draw indices. `docs/04` and `docs/05` were amended to state this explicitly, alongside partition's existing zero-draw exception.
- ~~A new `kind` byte gets an independent stream, so this **cannot perturb** any existing test's latency or loss sequence.~~ True for a different reason than stated: not because the stream is independent, but because there is no stream at all.
- Out of scope: making the throttle mutable at runtime — `M7-4` covers only the two faults #50 named.

**The trace format is the one place the four kinds are not independent.** `testdata/traces/*.golden` is `# netchaos-trace v1` with a fixed field list. Recording a throttle decision per unit changes that format even though no existing value moves — a golden diff, which `M3-3` treats as a contract-change signal. **Decided here: fields are emitted only for configured kinds** (not a `v2` header bump), applied the same way in `M7-7`, `M7-8` and `M7-9`.

**Sub-decisions this task answered**
1. **The option's shape:** `WithBandwidth(bytesPerSecond int)`, validated positive.
2. **Composition:** additively with `WithLatency`'s drawn delay, not superseding it — "supersedes" would make `WithLatency` silently inert whenever a throttle is configured, which is the wrong default for a library whose whole purpose is composing faults predictably.

**Files**

**How it was resolved**

Both open sub-decisions in the original task text were answered by the maintainer *before* any code was written, the same discipline `M7-3` used ahead of `M7-4`:

1. **The throttle is deterministic and takes no stream — a change from the task text, not an extension of it.** `size ÷ rate` has nothing random in it. The corrected framing: `M2-5`'s discipline binds fault kinds that have a stream to draw from; a kind with none has no draw index that can misalign, so it is not an exception to the discipline — the discipline does not apply to it, the same way it does not apply to partition's zero-draw short-circuit. `docs/04`'s draw-discipline paragraph and `docs/05`'s closing paragraph were both rewritten to say this, since leaving either as originally worded would have made it false the moment this shipped — the same "two `done` docs contradict each other" failure `M7-2` caught in `M6-9`.

### M7-7 — Fault kind: mid-stream connection reset

**Status:** done
**Issue:** [#53](https://github.com/jpgomesr/netchaos/issues/53), candidate 2 — decided by `M6-11`
**Decision (trigger, by the maintainer, before implementation):** **an imperative `Network` method targeting a peer pair** — `Network.Reset(peerA, peerB string)`, in the same family as `Partition`/`Heal` — not a per-unit drawn `Option`. **Depends on:** `M7-5` (the trace-format answer) — **superseded**, see "How it was resolved"
**Blocks:** `M7-10`

**Objective**
The clearest **gap** of the four rather than an enhancement. There is currently no way to make an established conn fail abruptly: `Partition` is the nearest thing and is deliberately a silent black hole — writes accepted and discarded, reads blocking to deadline — not an `ECONNRESET`. Testing "the peer dropped the connection" today means holding the server-side `net.Conn` and calling `Close` yourself, which a test of client-side reconnect logic should not have to do.

**This task is materially bigger than its three siblings.** It is **not** a per-unit delivery decision — it terminates a connection — so it reaches into `conn.Close`'s `closeOnce` teardown, the `closed` channel, in-flight `Read`/`Write` unblocking on other goroutines, and error shape, none of which the other three kinds touch. **If its design turns out to need its own decision task first, the way `M6-11` preceded implementation, splitting it is the right move rather than a planning failure.**

- Decide the error surface. `syscall.ECONNRESET` wrapped in `*net.OpError` matches `M6-2`'s uniform shape and what code under test would see from the real stack; reuse `conn.opError`.

**How it was resolved**

The maintainer's decision — an imperative method, not a drawn `Option` — changed the shape of this task from what the text above originally scoped, the same way `M7-5`'s "deterministic, not drawn" decision changed its own task text. Two consequences:

- **No `faultKind`, no stream, no evaluator entry.** `reset.go` is entirely outside `installFaultPolicy`'s composed evaluator — `Network.Reset` is a one-shot action against whichever connections currently exist for a peer pair, the same conceptual shape as `Close`, not a per-unit fault decision. This is why the file carries none of the draw-discipline machinery every other M7 fault kind needed.
- **A registry, not a per-unit read.** Unlike `Partition` (checked on every unit via `isPartitioned`), `Reset` needed a way to reach specific, already-established `*conn` objects at the moment it is called. `Network` gained `resetTargets map[pairKey][]*conn`, populated by `DialContext` after a connection establishes (under the same `pairKey` the fault policy for that connection already uses) and pruned by `conn.Close` via `deregisterReset`, so the registry does not grow unboundedly over a test that dials and closes many short-lived connections.

**The three ways `Reset` differs from `Partition`** were decided as part of working out the imperative-method shape, not separately negotiated:

1. **No effect on `Dial`.** Nothing about establishment changes; `Reset` only ever touches connections that already exist.
2. **Does not persist.** `Network.Reset` removes the target list for the pair from the registry *before* triggering each conn's reset (`delete(n.resetTargets, k)`), so a connection dialed for the same pair afterward registers itself fresh and is never affected by a reset that predates it — the real-RST analogy stated in the godoc.
3. **A no-op for an unestablished pair**, mirroring `Partition`/`Heal`'s existing no-op convention for the same reason: nothing to reset is not an error condition.

**Mechanism.** Each `conn` gets a `resetCh chan struct{}`, always allocated (even for a conn built without a `Network`, so `Read`/`Write` can select on it unconditionally) but only ever closed by `Network.Reset`'s call to the unexported `conn.triggerReset` (idempotent via its own `resetOnce`, independent of `closeOnce`). `Read` and `Write` check it first, ahead of the pipe's own state — a reset does **not** let already-buffered readable data drain first, unlike `Close`, which does. Once `resetCh` is closed it stays closed, which is what makes "stays reset" fall out of the channel's own semantics rather than a flag that has to be kept in sync.

**One bug in the tests, caught before merging.** `TestResetUnblocksInFlightRead` originally used a real `time.Sleep(20ms)` to let the reader goroutine reach its blocking point before calling `Reset` — a wall-clock timing assumption a slow or `-race`-instrumented CI runner could violate, exactly the flake shape a seed-driven library should not tolerate in its own tests. Rewritten to run inside a `synctest` bubble and use `synctest.Wait()` instead, mirroring `TestDialUnblocksOnHeal`'s (`partition_test.go`) existing "let every other goroutine durably block, then act" idiom — deterministic, and costs no real wall-clock time.

**Known follow-on cost for `M7-10`, worth naming now rather than discovering it during that merge:** `feat/m7-8-packet-duplication` and `feat/m7-9-data-corruption` were developed in parallel off `main`, and both add a new `faultKind` iota value to the same `rand.go` const block (`kindDuplicate` and `kindCorrupt` are each `= 2` on their own branch). Whichever of those two PRs merges second will hit a trivial const-block conflict, and — because a derived stream depends on the specific `kind` byte — that PR's own new golden trace (`duplicated-seed33.golden` or `corrupted-seed17.golden`) will need regenerating after the values settle, even though nothing about the fault's behaviour changed. A golden diff there is expected, not the contract-change signal `M3-3` otherwise trains a reviewer to treat it as. Recommend fixing the assignment before merging either — e.g. `kindDuplicate = 2`, `kindCorrupt = 3` regardless of merge order — so only one regeneration is ever needed and it is predictable. **Merge order for the four fault-kind PRs this milestone opened also matters to issue #53 itself:** only this task's PR (`M7-7`, the last of the four) carries `Closes #53` — merging it before `M7-8`/`M7-9` would close the umbrella issue with two kinds still unmerged.

**`-race`** needs `CGO_ENABLED=1`, unavailable on this dev machine (`AGENTS.md`) — confirmed on PR #69's CI run instead.

**How it was resolved**

The maintainer's one open sub-decision — whether the duplicate charges the pipe's buffer bound — was answered before implementation, the same discipline `M7-5` used for its two sub-decisions: **it charges**, so `installFaultPolicy`'s deliver closure does `p.bufBytes += len(dup)` for the second copy at the moment it is admitted, on top of whatever the original write's `tryWrite` already charged. `TestDuplicationChargesBothCopies` pins it directly: a bound sized to exactly two copies of one payload blocks a third, unrelated write.

Two details worth recording, both about the same shape of mistake `M7-5`'s design review caught before any code was written — a comment or invariant written for "one delivered copy per admitted unit" going quietly wrong once there could be two:

- **`fuzz_test.go`'s `checkPipeAccounting` comment** stated that the oversized-write rule was the *only* way `bufBytes` could exceed the bound with more than one non-empty buffered payload. That is no longer true package-wide — duplication is a second way — but the fuzz target itself drives a raw pipe with no fault policy installed, so it can never reach that path. The comment was narrowed to say so explicitly rather than left stating something false about the package as a whole.
- **The duplicate's timing is not drawn independently.** It reuses the exact `releaseAt` already computed for the original in the same `deliver` call, appended to `pending`'s tail. This keeps `pending`'s release-ordering invariant (each entry's `releaseAt >= every earlier entry's`) trivially true (equal, not strictly greater) and means `armLatencyForAppendLocked` only needs calling once, after the *original* entry's append — calling it again after the duplicate's append would be harmless (the guard only arms when the append made `pending`'s length exactly 1, which the second append of a pair never does) but is unnecessary, since the tail addition can never be an earlier deadline than what the timer is already armed for.

**Copies are independent slices**, not shared backing arrays (`append([]byte(nil), data...)` for the duplicate) — `TestDuplicateCopyIsIndependent` pins it, since a future corruption fault (`M7-9`) mutating one delivered copy in place must never affect the other.

**Trace fields extended `M7-5`'s per-scenario-declared answer** rather than inventing a new one: `scenario.fields` now supports `"dup"` alongside `"thr"`, rendered in a fixed canonical order (thr, then dup) regardless of declaration order, so a scenario naming neither — every one that predates this change — is byte-identical forever.

**How it was resolved**

The maintainer's one open sub-decision — the corruption granularity — was answered before implementation, the same discipline `M7-3`/`M7-5`/`M7-8` used: **a single bit**, not a byte or a drawn count. `stream.corruptionSite(n int)` (`rand.go`) draws a byte index bounded by the unit's length and a bit index bounded by 8, both through `boundedUint64` rather than `math/rand/v2`'s convenience API, matching `stream`'s existing constraint that every derived value stay bit-identical across Go versions, GOOS, and GOARCH.

Two details worth recording:

- **The site draw is conditional, not reserved.** Corruption's Bernoulli trial (`p.corrupt.bernoulli`) draws unconditionally on every unit past the partition gate, exactly like loss and latency. The follow-on `corruptionSite` draw only happens when that trial says yes *and* the unit is non-empty — a second, conditional draw from the same stream, the same shape `uniformDuration`'s rejection-sampling loop already uses ("one logical decision is not necessarily one raw draw"). This mirrors `M7-5`'s own conclusion about reserved-but-discarded draws: always drawing the site regardless of the coin flip's outcome would buy no forward compatibility, since the value would never be used.
- **Zero-length writes are the one edge the draw discipline creates.** A zero-length `Write` still draws corruption's Bernoulli trial (the unit reached the evaluator), but has no byte to flip — `corruptionSite` is skipped entirely rather than asked to index into an empty slice. `TestCorruptionOnZeroLengthWriteDoesNotPanic` pins it.

**Ordering relative to the timing stages.** Corruption is evaluated last in `installFaultPolicy`'s fixed order (after latency), placed there because content mutation and delivery timing are independent concerns — neither bandwidth's serialization delay nor latency's propagation delay reads the payload's bytes, so corruption's position among them doesn't change what either computes. It does have to run *before* the unit is appended to `readable`/`pending`, which the implementation does directly: `data[byteIndex] ^= 1 << bitIndex` mutates the pipe's already-private copy in place, before either delivery path runs.

**Ordering relative to duplication (`M7-8`), settled at merge time rather than in isolation.** With both kinds landed, `installFaultPolicy`'s order is partition, loss, bandwidth, latency, **corruption, then duplication** — corruption mutates content first, so a duplicated unit's second copy carries whatever corruption already did to the first, rather than an independently corrupted copy. `docs/04` and `docs/05` state this explicitly.

**The `kindDuplicate`/`kindCorrupt` iota collision, resolved.** `feat/m7-8-packet-duplication` and this branch were developed in parallel off `main`, and both added a new `faultKind` value to the same const block (`kindDuplicate = 2` on one, `kindCorrupt = 2` on the other) — flagged as a known merge cost in `M7-7`'s "How it was resolved." Resolved by keeping `kindDuplicate = 2` (already shipped, so its golden stayed valid) and moving `kindCorrupt` to `3`. That shifted this task's own derived stream, so `corrupted-seed17.golden` needed regenerating after the merge — the *only* golden that changed; `clamping-seed7`, `composed-basic-seed42`, `throttled-seed99`, and the newly-merged `duplicated-seed33` are all byte-identical (verified via `git diff --stat`, zero lines for those four). A golden diff here was the expected consequence of the byte reassignment, not a regression.

**How it was resolved**

Both maintainer decisions landed as recommended in the task text, and one constraint surfaced during implementation that the task text hadn't named.

**No `Network` → trace path existed before this task.** Recorders live on `pipe.trace`, reachable only from a `*conn`. The only conn registry that already existed, `Network.resetTargets` (`M7-7`), is pruned on `conn.Close` by design — a `Network.Trace()` built on it would lose every closed connection's trace, which is the common case (`defer c.Close()`). The fix: register the *recorders*, not the conns. `Network` gained `traces []traceHandle`, a slice of `{ordinal, side, *traceRecorder}` never pruned, appended to once per direction in `DialContext` right after `registerReset`. Three things fall out of that shape rather than needing separate handling: nothing beyond a small struct is retained (no pipe buffers, no deadline timers survive via this path), append order is dial order is ordinal order so `Trace()`'s canonical `(Ordinal, Side, Seq)` needs no sort, and the registry is visibly a different thing from `resetTargets` — different lifetime, stated reason — rather than an inconsistency with `M7-7`.

**The `Network` type doc's own "revisit this only if a resource appears that is not scoped to a single conn" clause is exactly what `traces` is.** Adding a Close method would still buy nothing — there is no goroutine or timer to reap, only recorder pointers whose memory dies with `Network` itself — so the fix was to amend the *reasoning*, not add a method: the "nothing to reap" claim was always about asynchronous work, not about every field's lifetime matching a conn's.

**`captureTrace` (`reproducibility_test.go`) was not rebuilt on `Trace()`**, even though both now produce the same canonical order. The harness's coverage rule — a scenario must return every conn end it created, or half the directions go uncaptured — is what the golden-trace tests depend on, and `Trace()` has no equivalent rule (it returns everything a `Network` has ever dialed, with no way to assert "and nothing else"). The file's own comment, which said "No new exported API" and pointed at `M2-1`'s deferral as still open, was the one piece of `done` prose this task made false — rewritten to say both are now true (the harness itself added no API; the deferral it cited is resolved elsewhere) and why the harness still reads the recorders directly rather than through `Trace()`.

**Golden traces are untouched.** `Trace()` reads through `traceRecorder.snapshot()` — the existing copy path `TestTraceSnapshotIsACopy` already covers — so nothing about how or when an event is recorded changed; `git diff --stat testdata/` is empty.
